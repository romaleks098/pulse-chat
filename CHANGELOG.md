## 1. Регламент внесения изменений

Каждый раз, когда в проект вносятся любые правки:
1. **Запрет на утечку секретов**: Никогда не писать в код, тесты, README, render.yaml или отчёты пароли, токены, ключи API и полные строки подключения.
2. **Проверка секретов перед коммитом**: Запустить `npm run check:secrets`.
3. **Проверка сборки**: Запустить `npm run build` (клиент и сервер должны собираться без ошибок).
4. **Проверка автотестов**: Запустить `npm test` (все тесты должны быть зелёными).
5. **Обязательная запись в `CHANGELOG.md`**: Описать:
   - Версию / Дату / Хэш коммита
   - Категорию изменений (Fix / Feature / Security / Refactor)
   - Какая проблема была и её корневая причина

## 2. Архитектура проекта

- **Клиент (`client/`)**:
  - React 19, TypeScript, Vite, Tailwind CSS, Lucide Icons.
  - Управление состоянием: `ChatContext.tsx`, `ThemeContext.tsx`, `CallContext.tsx`.
  - Дизайн-токены: CSS-переменные на `:root` (поверхности, текст, пузыри, акцент, радиусы, шрифты, плотности).
  - Базовые UI-примитивы (`client/src/components/ui/`): `Avatar`, `Badge`, `ContextMenu`, `Modal`, `Tabs`, `Toast`, `Slider`, `ColorPicker`.
- **Сервер (`server/`)**:
  - Node.js, Express, TypeScript, Socket.io, Multer, better-sqlite3 (локально) / pg (в проде).
  - Маршруты: `/api/auth`, `/api/conversations`, `/api/messages`, `/api/health`, `/api/sync`.
  - Защита: OAuth 2.0 PKCE со state в БД, `timingSafeEqual` для Telegram Webhook, HttpOnly cookies.
- **Интеграция с мобильными платформами**:
  - Capacitor Android SDK (`client/android`), PWA Manifest, Service Worker.

### Версия 1.5.0
**Дата:** 23 октября 2026  
**Категория:** Fix / Database / Data Integrity  
**Описание проблемы:**
1. Если у пользователя в базе создавалось несколько строк «Избранного», простое скрытие дубликатов в контроллере приводило к тому, что сообщения, отправленные во второй дубликат, становились недоступными.
2. Во вкладке «Группы» условие фильтрации включало каналы (`c.type === 'group' || c.isChannel`), из-за чего каналы дублировались и во вкладке «Группы», и во вкладке «Каналы».

**Решение:**
1. В `server/src/db.ts` реализована функция `healAndConsolidateSavedMessages()`:
   - Автоматически находит всех пользователей с несколькими чатами «Избранное».
   - Выбирает канонический чат (с наибольшим числом сообщений или самый ранний).
   - Перепривязывает все сообщения: `UPDATE messages SET conversation_id = <canonical_id> WHERE conversation_id = <dup_id>`.
   - Удаляет дублирующие членства и записи из таблицы `conversations`.
   - Вызывается при каждом старте сервера и при вызове `POST /api/conversations/saved`.
2. В `client/src/components/Sidebar.tsx` фильтр групп строго ограничен: `c.type === 'group' && !c.isChannel`.

**Затронутые файлы:**
- `server/src/db.ts`
- `server/src/routes/conversations.ts`
- `client/src/components/Sidebar.tsx`

### Версия 1.3.0
**Дата:** 22 октября 2026  
**Категория:** Security / OAuth 2.0 / Webhooks  
**Описание проблемы и решение:**
1. **Google & GitHub OAuth exchange:**
   - Ошибки обмена токенов подробно логируются (invalid_client, redirect_uri_mismatch, invalid_grant) без утечки `client_secret` и одноразового `code`.
   - Значения `state` и PKCE `code_verifier` перенесены из оперативной памяти процесса в базу данных (таблица `pulse_oauth_state`) с TTL 10 минут. Это устранило ошибку сброса авторизации при перезапуске инстанса Render.
   - Записи `pulse_oauth_state` удаляются сразу после успешного подтверждения (защита от replay attack).
2. **Telegram Webhook:**
   - Добавлена строгая проверка постоянного времени `crypto.timingSafeEqual` для заголовка `X-Telegram-Bot-Api-Secret-Token`.
   - Запросы без секретного токена отклоняются с кодом 403.
   - Регистрация вебхука через `setWebhook` выполняется с обязательным параметром `secret_token`.
3. **Безопасные Cookies:**
   - Все аутентификационные куки снабжены флагами: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`.

### Версия 1.1.0
**Дата:** 21 октября 2026  
**Категория:** Bugfix / Backend / Persistence  
**Описание проблемы:**
На облачном хостинге Render данные (пользователи, чаты, сообщения) пропадали после перезапуска сервиса, так как сервер молча откатывался на временную SQLite базу на эфемерном диске.

**Решение:**
1. В `GET /api/health` добавлены поля: `provider` ("postgres" или "sqlite"), `database_ok` (true/false), `server_epoch`.
2. Логирование при старте: выводится только тип провайдера и флаг наличия `DATABASE_URL` (задан / не задан) без вывода самого значения.
3. В продакшене (`NODE_ENV=production`) строго запрещена работа на SQLite: при отсутствии валидного `DATABASE_URL` процесс завершается с понятной ошибкой в логах (`process.exit(1)`).
4. Реализован надёжный пул подключений PostgreSQL с поддержкой PgBouncer и SSL (`rejectUnauthorized: false`).
